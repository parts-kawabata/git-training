SECTION 17

過去に戻って新規ブランチを作成、作業をやり直したい

過去の修正をやり直したいときは、そのコミットにチェックアウトで移動してから、ブランチを生やすことで、別の修正をすることができます。

元の履歴はそのまま。過去の時点から「別の未来」を作り直せます。
SECTION 18

過去のコミットを打ち消したい（リバート）

リバート（revert＝元に戻す）は、コミット1件を逆適用することができます。

過去のコミット自体を削除するわけではなく、あくまでも反対の内容で新規コミットを作ることで、過去の変更を打ち消すというところがポイント。別のコミットが間に挟まっている場合でもリバートできます。

Bのコミットは消えずに残ったまま。間にCがあってもOK。
コマンドで操作する場合（読み飛ばしてもOK）
$ git revert コミットID ← コミットIDを指定してリバートする
SECTION 19

履歴を一直線にしたい（リベース）

ブランチを統合するのはマージ以外にも、リベース（rebase＝土台を付け替える）というやり方もあります。

例として、「ナビゲーション」と「Facebookボタン」の作業を統合する場合を考えます。マージした場合は、2つの作業が単に時系列に並んで、パッと見たときに何が変更されたのかよく分かりません。リベースした場合は、「ナビゲーションを修正して、Facebookボタンを設置したんだな」ということがパッと見て分かりやすくなります。

マージ

  • 過去のコミットは改変されずに、マージするためだけの新しいコミットが作成される

リベース

  • もともとのコミットが改変されてリベース先のブランチに乗っかり、履歴が一直線になる

マージしてもリベースしても、統合後のソースコードは一緒。違うのは、生成される履歴の形です。

⚠ 注意

リベースは履歴を改変するので若干の危険性があります。すでにリモートリポジトリ上に存在するコミットは、リベースしないように気をつけましょう。
慣れないうちはマージを使っておけばよいです。

コマンドで操作する場合（読み飛ばしてもOK）
$ git rebase master ← リベース先のブランチを指定する
SECTION 20

コミットを1つにまとめたい（スカッシュ）

スカッシュ（squash）とは、コミットをひとつにまとめる方法で、「圧縮する・押しつぶす」という意味があります。「ちょっと修正」「タイプミス修正」のような細かいコミットを、意味のあるひとまとまりに整理できます。

押しつぶして、ひとつに。

※スカッシュは「インタラクティブリベース」というモードで行います。

⚠ 注意

コミットがすでにリモートリポジトリ上に存在する場合、履歴を改変してしまうと、他のメンバーのリポジトリと差異ができてしまい、みんなを混乱させてしまいます。そのコミットが自分のローカルリポジトリにしか存在しないことを確認してから操作しましょう。

SECTION 21

プルは実際には何をやっているの？

実は、リモートブランチとローカルブランチの間には、リモート追跡ブランチというものが存在します。

ブランチ説明
リモートブランチ
  • リモートリポジトリの中にある
リモート追跡ブランチ
  • ローカルリポジトリの中にある
  • リモートブランチをローカルにミラーリング（コピー）しただけのもの
  • 読み取り専用
ローカルブランチ
  • ローカルリポジトリの中にある
  • 普段コミットするブランチ
GitHubの変更は、いったん「リモート追跡ブランチ」に届き、それからローカルブランチに合流します。

まず、リモートブランチ、リモート追跡ブランチ、ローカルブランチが同じ状態になっているのが理想。リモートブランチでコミットが進んだら、リモート追跡ブランチにも反映されます（フェッチ）。それをローカルブランチにマージする。この2工程をまとめてやってくれるのがプルです。

SECTION 22

リモートリポジトリから最新の状態を取得したい（フェッチ）

リモートリポジトリの最新の状態は取得したいけれど、まだローカルブランチには反映させたくないという場合は、フェッチ（fetch＝取ってくる）を使います。

フェッチしただけでは、リモート追跡ブランチ（origin/〇〇）が更新されるだけ。この時点ではローカルブランチは更新されていません。マージすることで、はじめてローカルブランチが更新されます。

💡 おすすめの習慣

昼休憩中や寝ている間に、誰かが新しくコミットを進めているかもしれません。作業を始める直前にフェッチするのがおすすめ。こまめにフェッチすることで、事故を防ぐことができます。

コマンドで操作する場合（読み飛ばしてもOK）
$ git fetch ← リモートリポジトリの全ブランチをリモート追跡ブランチの上にダウンロードしてくる
$ git merge origin/master ← リモート追跡ブランチをローカルブランチにマージする
SECTION 23

不要になったリモート追跡ブランチを削除したい（プルーン）

プルーン（prune＝枝を刈り込む）は、リモートリポジトリですでに消されたブランチを、ローカルリポジトリでも一掃してくれるオプションです。

リモートブランチを削除する方法

  1. GitHubでリモートリポジトリを開くGitHub
  2. ブランチ一覧からクリックで削除するGitHub
  3. Source Treeでフェッチして、リモート追跡ブランチの削除を反映する自分のPC
  4. Source Treeでローカルブランチも削除して完了自分のPC

定期的にフェッチ・プルーンして、リモートリポジトリと同じ状態を保つと作業しやすくなります。

コマンドで操作する場合（読み飛ばしてもOK）
$ git branch -a ← すべてのブランチを確認する（リモート追跡ブランチを含む）
$ git fetch --prune ← リモートリポジトリで消えた追跡ブランチを消去する
$ git branch -d ブランチ名 ← 任意のローカルブランチを削除する
SECTION 24

直近のコミットメッセージを修正する

「コミットメッセージに誤字があった！」というとき、直近のコミットであればすぐに修正することができます（amend＝修正する）。

⚠ 注意

この方法が使えるのはプッシュ前に限ります。

コマンドで操作する場合（読み飛ばしてもOK）
$ git commit --amend ← 直前のコミットメッセージを修正する（viが立ち上がる）

※「vi」は黒い画面で使うテキストエディタ（文章を編集する道具）の名前です。

SECTION 25

未コミットのファイルを一時退避する（スタッシュ）

スタッシュ（stash）は英語で「こっそりしまう」「隠しておく」といった意味があります。その名の通り、作業ディレクトリの変更内容を、一時的に別の場所へどけておくことができます。どけておいた変更内容は、あとで復元できます。

こんなときに

作業途中の内容を一時退避して、ブランチを移動したいときやプルしたいときに役立ちます。
たとえば「作業の途中で、急ぎのバグ修正を頼まれた！」という場面。机の上の書きかけの書類をいったん引き出しにしまって、急ぎの仕事をすませたら、また取り出すイメージです。

スタッシュの使い方

📥1. 一時退避作業途中の内容を、スタッシュで一時退避
📤2. 復元割り込み作業をすませたら、一時退避しておいた変更内容を復元
コマンドで操作する場合（読み飛ばしてもOK）
$ git stash save ← スタッシュを保存する
$ git stash list ← 過去に保存したスタッシュのリストを見る
$ git stash apply ← スタッシュリストの一番上の変更を適用する
$ git stash drop ← スタッシュリストの一番上の変更を捨てる

※新しいバージョンのGitでは、git stash save の代わりに git stash push（または単に git stash）が推奨されています。

SECTION 26

別ブランチから特定のコミットのみを取り込みたい（チェリーピック）

チェリーピック（cherry-pick）とは、英語の慣用句で「熟れているサクランボだけを選んで摘み取る＝いいとこ取り」という意味。その名の通り、好きなコミットを選んで摘み取ることができます 🍒

コミットを「移動」するのではなく「コピー」。元のコミットは残ったままです。

あくまでも特定のコミットを、今いるブランチ上にコピーしてくるだけであって、コミットを移動させるわけではないため、元のコミットは残ったまま。間違えて違うブランチにコミットしてしまった場合などに使えます。

コマンドで操作する場合（読み飛ばしてもOK）
$ git cherry-pick コミットID ← 任意のコミットを、今いるブランチ上にコピーしてくる
SECTION 27

コミットに目印をつける（タグ）

タグを使うと、履歴上の重要なポイントに目印をつけることができます。分かりやすい名前の目印をつけておくことで、後で履歴を探しやすくなります。本のしおりや付箋のようなものです。

重要なコミットに名前つきの目印。あとから一発で見つけられます。

こんなときに便利

📱アプリ開発リリースしたときにバージョン番号のタグをつける
📦受託開発納品したときに日付のタグをつける（2026-04-23）
🌐Web開発リニューアルオープンしたときにタグをつける（2026-renewal）
コマンドで操作する場合（読み飛ばしてもOK）
$ git tag タグ名 ← 新規タグを作る
$ git push origin タグ名 ← タグをリモートリポジトリに共有する
$ git tag -d タグ名 ← ローカルリポジトリのタグを削除する
$ git push origin --delete タグ名 ← リモートリポジトリのタグを削除する
SECTION 28

間違えてHEADに直接コミットしてしまったら

コミットした際、コミットメッセージに「HEAD」という印があればdetached HEAD（デタッチド・ヘッド）状態です。これはどのブランチにも所属しない“無所属”状態になったということ。

このままコミットを積み重ねて突き進むこともできますが、目印がないため、次にチェックアウトしたときに戻れなくなってしまいます。

HEADってなに？

「自分が今いる場所」を指す目印です。CHAPTER2・3で出てきた「今ココ！」の正体がHEADです。

detached HEAD状態でコミットすると

通常の状態

  • 基本的に、HEADはブランチを指している

detached HEAD状態

  • HEADが直接コミットを指してしまっている状態

HEADが分離した状態でコミットすると、ちゃんとコミットしたように見えます。しかし、そのまま別のブランチにチェックアウトすると、detached HEAD状態のコミットがなくなってしまいます。

💡 慌てなくて大丈夫

うっかりHEADに直接コミットしてしまっても、今いるコミットを新規ブランチにしたら、detached HEAD状態が解消され、「HEAD」と表示されていたところがブランチに変わります。

コマンドで操作する場合（読み飛ばしてもOK）
$ git checkout -b ブランチ名 ← detached HEAD状態になっていることに気付いたら、そこから新規ブランチを作ってそっちに移動する
SUMMARY

まとめ

やり直し・履歴の整理

  • 過去に戻って作業をやり直したいとき → 任意のコミットを指定して、新規ブランチを生やす
  • リバート → 過去のコミットと逆の内容を新規にコミットすることで、安全に打ち消すことができる
  • リベース → 履歴を一直線にできる（ただし、履歴を改変するので若干の危険性あり）
  • すでにリモートリポジトリ上に存在するコミットは、リベースしないように気をつける（慣れないうちはマージを使っておけばよい）
  • コミットをまとめたいとき → インタラクティブリベースモードにしてスカッシュする（ただし、履歴を改変するので若干の危険性あり）
  • すでにリモートリポジトリ上に存在するコミットは、インタラクティブリベースしないように気をつける
  • 直近のコミットメッセージは、プッシュ前ならamendで修正できる

リモートとのやり取り

  • フェッチは、リモートリポジトリから更新内容をダウンロードしてきて、ローカルリポジトリ内のリモート追跡ブランチを更新する
  • つまり、リモート追跡ブランチ（origin/〇〇）が更新されるだけ。この時点ではローカルブランチは更新されていない
  • マージすることで、はじめてローカルブランチが更新される
  • フェッチとマージを合わせた機能がプル

便利技

  • スタッシュ → 未コミットのファイルを一時退避できる
  • チェリーピック → 任意のコミットを、今いるブランチの上にコピーしてこれる
  • タグで、履歴上の重要なポイントに目印をつけることができる

detached HEAD

  • detached HEAD状態でコミットしない
  • detached HEAD状態でコミットしてしまった場合は、慌てず新規ブランチを作ってそっちに移動（チェックアウト）する
